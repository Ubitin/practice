# vector 迭代器失效与 reserve：什么时候防得住

> 背景：你添加的《vector 的实现细节.txt》说明了 vector 的扩容机制（size 与 capacity 分离、容量不足时分配 2N 新数组、拷贝旧数据、释放旧内存、均摊 O(1)）。
> 由此引出的问题：**一开始就用 `reserve()` 预留足够内存，后续 insert / resize 等操作能否避免反复拷贝与地址变动，从而避免迭代器失效？**
> 演示程序：`test_\03.cpp`（与 `01.cpp`、`02.cpp` 同目录，可自行编译运行验证）。

---

## 1. 结论（先记这一句）

**对一半。** reserve 能防住"扩容搬家"那一类迭代器失效，但**防不住"元素位移"那一类**——后者与容量无关。

**两类失效的本质区别：**

| 失效类型 | 原因 | reserve 能否防 |
|---|---|---|
| **扩容搬家型** | 容量不足 → 分配 2N 新数组 → 整块内存迁移，旧内存释放，所有旧迭代器悬垂 | ✅ 能防 |
| **元素位移型** | 中间 insert/erase → 插入/删除点之后的元素在同一块内存里整体挪位，旧迭代器指向的位置被顶替 | ❌ 防不了 |

## 2. 运行结果实证（test_\03.cpp 实际输出）

```
=== A. reserve(100) 后 push_back 50 次 ===
itA 指向的值: 1      ← 保存的迭代器仍有效
两地址相同 = 内存没搬家 ✅

=== B. 不 reserve，push_back 触发扩容 ===
扩容前 &w[0]=0x...ec0  扩容后 &w[0]=0x...5c0
地址变了 = 旧内存已释放 = 之前的指针/迭代器全部作废（悬垂）✗

=== C. reserve(100) 后中间 insert（容量足够）===
insert 前 *itC = 40
insert 后 *itC = 30   ← 指向的值变了！位移发生 ✗
u = 10 999 20 30 40

=== D. reserve(100) 后末尾 insert ===
*itD = 1（仍有效）；注意 end() 本身失效了，要重新取 ✅
```

## 3. 完整失效规则表

| 操作 | 容量足够（已 reserve） | 容量不足 |
|---|---|---|
| `push_back` / 末尾 `insert` / `resize` 变大 | 已有元素迭代器**有效**（仅 `end()` 失效） | **全部失效**（搬家） |
| **中间** `insert` | 插入点及之后**失效**（位移） | 全部失效 |
| `erase` / `pop_back` / `resize` 变小 | 被删元素失效，其余**有效** | 同左（无搬家） |

> 标准（cppreference）原文结论：insert 使插入点**及之后**的迭代器失效，若发生重分配则全部失效；erase 使被删点及之后的迭代器失效。中间操作的"失效"即使实测能读出值，也属于**未定义行为**，绝不能依赖。

## 4. 三个补充细节

1. **`end()` 永远失效**：任何末尾操作后 `end()` 的位置都变了，要重新取——这就是"迭代器随用随取"守则的由来。
2. **reserve 只管"不扩容"**：insert 的总量若超过预留容量，照样搬家；reserve 也不改变 `size()`。
3. **删除操作天然安全**：`pop_back`、删末尾、`resize` 变小只是"扔掉队尾"，前面的元素原地不动，迭代器不受影响。

## 5. 记忆钩子

> **reserve 防的是"整栋楼搬家"，防不了"楼内的人挪座位"。**
> 扩容 = 整栋楼换地址（reserve 可防）；中间 insert/erase = 楼内住户移位（reserve 无效）。

## 6. 实用结论

- 竞赛/刷题：确定要连续 `push_back` 共 n 次时，先 `v.reserve(n)`——既省去反复拷贝的时间，又保证期间保存的迭代器安全。
- 只要碰了**中间** `insert/erase`，就放弃"保存迭代器跨操作使用"的想法，老实随用随取 `v.begin()`/`v.end()`。
- 只做末尾增删时，reserve 之后可以放心保存指向已有元素的迭代器。
