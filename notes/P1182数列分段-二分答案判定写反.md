## 三、⭐ 深度归因：你的程序实际在算什么

我做了个假设检验——**你的输出是不是恰好等于「前 m−1 个数的前缀和」？**

```
n=6 m=1 a=[3,10,4,5,14,10]   你的=0    前(m-1)项和=0    ✓
n=2 m=2 a=[5,5]              你的=5    前(m-1)项和=5    ✓
n=8 m=6 a=[10,4,1,6,12,16,1,11] 你的=33  前(m-1)项和=33  ✓
n=1 m=1 a=[3]                你的=0    前(m-1)项和=0    ✓
...
→ 命中 15 / 15
```

**15/15 全中。** 你的程序在算的是：

$$\text{输出} = \sum_{i=1}^{m-1} a_i$$

而不是"最小化最大段和"。这也解释了为什么样例（m=3，前 2 项和 = 4+2 = 6）恰好对——**巧合**。

### 为什么会退化成这个？逐步推导

```cpp
bool p(ll x){
    ...
    ll temp = 0;
    for(ll i = n;i>=0;--i){
        if(prev[i] <= temp + x){ temp = prev[i]; res ++; }
    }
    return res >= m;
}
```

1. `temp` 从 0 开始，第一次满足 `prev[i] <= x` 时 `res = 1`、`temp = prev[i]`
2. **关键**：下一轮的条件是 `prev[i-1] <= temp + x = prev[i] + x`。而 `prev` 单调不减、`x >= 0`，所以 `prev[i-1] <= prev[i] <= prev[i] + x` —— **必然成立**
3. 于是**第一次成功之后，后面每个 `i` 都会成功**，`res` 一路加到底

所以 `res = i₀ + 1`，其中 $i_0=\max\{i: pre[i] \le x\}$（从 n 往下第一个满足的）。

$$p(x) \text{ 为真} \iff i_0(x)+1 \ge m \iff i_0(x) \ge m-1 \iff pre[m-1] \le x$$

二分会找到满足它的最小 `x`，也就是 $\boxed{pre[m-1]}$。**推导与实测完全吻合。**

> ⚠️ 注意：**问题不在"从右往左贪心"这个方向**（对正数来说，从左或从右贪心得到的段数一样）。问题在**不等式方向**和**返回值方向**。

## 四、四处 bug 逐条

### ★① 贪心的不等式方向反了

要判断的是"当前这一段的和是否 ≤ x"。

从左往右的写法（推荐）：

```cpp
ll cnt = 1, cur = 0;
for (ll i = 1; i <= n; ++i) {
    if (cur + a[i] <= x) cur += a[i];     // ✅ 装得下就继续装
    else { ++cnt; cur = a[i]; }            // 装不下，另起一段
}
```

如果坚持从右往左：

```cpp
// temp = 当前这一段右端点的前缀和；新左端点在 i → 这一段和 = temp - prev[i]
// 要求 temp - prev[i] <= x  ⟺  prev[i] >= temp - x        ← 应该是这个
if (prev[i] >= temp - x) { temp = prev[i]; ++cnt; }         // ✅
```

你的代码写的是 `prev[i] <= temp + x`，**不等号两侧的减号都变成了加号**，于是条件从"段和够小"变成了"几乎恒真"。

### ★② `return res >= m` 方向反了

**要判的是"最少需要几段 ≤ m"**，不是 `≥ m`：

```cpp
return cnt <= m;      // ✅
```

**概念点：为什么 `cnt <= m` 就代表可行？**

`cnt` 是"每段和 ≤ x"前提下的**最少段数**。只要 `cnt <= m`：

- 如果 `cnt < m`，就把某些段**继续拆细**（拆了每段和只会更小），总能凑到恰好 m 段
- 前提是 `x >= max(a[i])`，保证每个单元素自成一段 —— 这正是下界要取 `max(a)` 的原因

`cnt > m` 则无论怎么合并都放不下，x 不可行。

### ★③ 下界 `l = 0` 不对，应该是 `max(a[i])`

**每段至少含一个数**，所以"每段和的上限"不可能小于最大的那个元素。下界取 0 会让二分去尝试一堆根本不可能的 `x`。

### ★④ 上界 `r = 1e9` 太小 —— 这是独立的第二个致命错

P1182 的范围是 `n ≤ 10^5`、`a_i ≤ 10^8`，所以 **总和可达 10^13**。答案上限是"所有数放一段"，也就是总和。

**实测**：

| 输入 | 正确答案 | 你的代码（上界 1e9） |
|---|---|---|
| `100 1` / 100 个 `1e8` | **10000000000**（1e10） | `0` |
| `1000 7` / 1000 个 `1e7` | **1430000000**（1.43e9） | `60000000` |

第二组的答案 1.43e9 **已经超过 1e9** —— 就算把 check 修对，**二分也够不到正确答案**。

```cpp
ll hi = 0;
for (ll i = 1; i <= n; ++i) hi += a[i];   // ✅ 上界 = 总和
```

> 注意这里 `hi` 必须是 `long long`：`10^5 × 10^8 = 10^13`，`int` 直接溢出。

### ☆⑤ 每次 check 都重建前缀和数组（多余）

```cpp
bool p(ll x){
    vector<ll> prev(n + 1);        // ⚠️ 每次调用都分配 + 算一遍 O(n)
    ...
}
```

判定用一次从左到右的贪心（O(n)、一个 `cur` 变量）就够，**根本不需要前缀和**。虽然本题数据量下不至于 TLE，但白跑一倍工作量，而且这个前缀和正是导致你把判定写复杂的根源。

## 五、正解

```cpp
#include <bits/stdc++.h>
using namespace std;
using ll = long long;

int main() {
    ios::sync_with_stdio(false); cin.tie(nullptr);
    ll n, m; cin >> n >> m;
    vector<ll> a(n + 1);
    ll lo = 0, hi = 0;
    for (ll i = 1; i <= n; ++i) {
        cin >> a[i];
        lo = max(lo, a[i]);        // ★ 下界 = 最大元素
        hi += a[i];                // ★ 上界 = 总和（long long！）
    }

    auto ok = [&](ll x) -> bool {
        ll cnt = 1, cur = 0;
        for (ll i = 1; i <= n; ++i) {
            if (cur + a[i] <= x) cur += a[i];
            else { ++cnt; cur = a[i]; }
        }
        return cnt <= m;           // ★ 最少段数 ≤ m
    };

    while (lo < hi) {
        ll mid = lo + (hi - lo) / 2;   // 下取整，配 hi = mid（求最小可行值）
        if (ok(mid)) hi = mid;
        else         lo = mid + 1;
    }
    cout << lo << '\n';
    return 0;
}
```

**复杂度 O(n log(sum))**，`n=10^5`、`sum=10^13` 时约 `10^5 × 44 = 4.4×10^6`，轻松通过。

**回归测试**：

|---|---|---|
| `5 3` / `4 2 4 5 1` | 6 | **6** ✔ |
| `3 1` / `1 2 3` | 6 | **6** ✔ |
| `3 3` / `1 2 3` | 3 | **3** ✔ |

## 七、自查

1. 你的 `p(x)` 里 `prev[i] <= temp + x` 应该改成什么？为什么？
2. 为什么 `cnt <= m` 就能代表"可以分成恰好 m 段"？这依赖 `x` 的什么下界？
3. P1182 的答案最大能到多少？上界该取什么？为什么 `int` 会溢出？
4. 下界为什么是 `max(a[i])` 而不是 0 或 1？
5. 求"最小可行值"时，`mid` 该上取整还是下取整？配套改哪个边界？
6. 为什么这道题的样例（m=3）恰好能过？它掩盖了几个 bug？

**答案要点**
1. 改成 `prev[i] >= temp - x`。因为从右往左时这一段的和 = `temp - prev[i]`，要求它 ≤ x。写成 `<= temp + x` 后，由于 `prev` 单调不减且 `x ≥ 0`，第一次成功之后每一轮都必然成立，判定就恒真了。
2. 因为 `cnt` 是"每段和 ≤ x"下的**最少**段数。若 `cnt < m`，把某些段继续拆细即可凑到恰好 m 段（拆了每段和只会更小）。这依赖 `x ≥ max(a[i])`，保证每个单元素能自成一段——这就是下界取 `max(a)` 的原因。
3. 最大约 `n × max(a) = 10^5 × 10^8 = 10^13`，远超 `int`（约 2.1×10^9）。上界应取总和 `sum(a)`（此时把所有数放一段必定可行），且必须用 `long long`。
4. 每段至少含一个数，段和的上限不可能小于最大的那个元素本身。取 0 会让二分去尝试不可能的 `x`。
5. 下取整 `mid = lo + (hi-lo)/2`，配 `hi = mid`。上取整配 `lo = mid`；配错会死循环。
6. 样例 `m=3` 时"前 m−1 项和"恰等于 `4+2=6`，与正确答案 6 相同。它同时掩盖了"判定方向反了"和"上界太小"两个独立 bug——**必须先修成一个正确的解，才能暴露另一个**。
