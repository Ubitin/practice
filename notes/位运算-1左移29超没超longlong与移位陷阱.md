# `(1 << 29)` 超没超 long long？—— 没超；但这个问法背后有三个真坑

> **触发点**：你问"`(1 << 29)` 是否超出 long long 的范围"。
> **一句话结论**：**`1 << 29` = 536,870,912，连 `int` 都远远装得下**（`INT_MAX` ≈ 2.1e9），`long long` 更是差着 10 个数量级。真正的坑不是"29"这个数字，而是：
> ① **`1 << n` 是在 `int` 里算的**——`n ≥ 31` 就废了，跟你存进什么类型无关；
> ② **算完再存进 `long long` 救不回来**（溢出发生在赋值之前）；
> ③ **移位位数 ≥ 类型宽度是 UB**——实测同一个 `1 << 32`，"编译期折叠"和"运行时算"给出**两个不同的结果**。

---

## 一、先直接回答：范围够不够

| 表达式 / 常量 | 值 | 结论 |
|---|---|---|
| `1 << 29` | **536,870,912**（5.37 亿）| ✔ `int` 都装得下 |
| `INT_MAX` | 2,147,483,647（21.5 亿）| 还有约 **4 倍**余量 |
| `LLONG_MAX` | 9,223,372,036,854,775,807（9.22e18）| 还差 **约 10 个数量级** |

所以答案是：**远没超，超得不能再不超。**

> 但如果你是想拿 `1 << 29` **当 INF 用**（5.37 亿），要注意它并不是"足够大"：距离/和这一类量很容易超过 5.37e8（比如 n=1e5 个 1e8 相加 = 1e13）。当 INF 请用 `0x3f3f3f3f`（≈1.06e9）或 `(ll)1e18`。见手册 §6.6。

---

## 二、真正该问的是：`1 << n` 的边界到底在哪（实测）

`test_\38.cpp` 在 `-O2 -std=c++17` 下的真实输出（用 `volatile` 挡住常量折叠）：

```
  n=28 : 1<<n = 268435456      1LL<<n = 268435456
  n=29 : 1<<n = 536870912      1LL<<n = 536870912        <- 你问的这个
  n=30 : 1<<n = 1073741824     1LL<<n = 1073741824
  n=31 : 1<<n = -2147483648    1LL<<n = 2147483648       <- int 崩了
  n=32 : 1<<n = 1              1LL<<n = 4294967296
  n=33 : 1<<n = 2              1LL<<n = 8589934592
```

汇总成"可用边界表"（背这张表就够）：

| 目标类型 | 最大合法的 2 的幂 | 再往上一位会怎样 |
|---|---|---|
| `int`（4 字节，有符号）| `1 << 30` = 1,073,741,824 | `1 << 31` = **-2147483648**（溢出成负的）|
| `unsigned`（4 字节）| `1u << 31` = 2,147,483,648 | `1u << 32` → 移位位数超宽，UB |
| `long long`（8 字节）| `1LL << 62` = 4,611,686,018,427,387,904 | `1LL << 63` = **-9223372036854775808**（= `LLONG_MIN`）|

记忆点：**`int` 只能到 2³⁰，`long long` 只能到 2⁶²**（各留一位给符号位）。

---

## 三、坑 1：算完再存进 `long long` 没用

```cpp
volatile int n31 = 31;
long long a = 1 <<  n31;    // 实测 -> -2147483648   （负的！）
long long b = 1LL << n31;   // 实测 ->  2147483648
```

原因：**赋值发生在右边全部算完之后**。`1 << 31` 的类型由**操作数**决定——`1` 是 `int`，所以整个表达式就是 `int`，先在 `int` 里溢出成负数，**再**把这个负数转成 `long long`（符号扩展）。

> **口诀：结果类型由操作数决定，不由左边的变量决定。**
> 同理的还有 `long long x = 1e9 * 1e9;`（两个 `int` 相乘溢出，存进 long long 也晚了一步）→ 要写 `1LL * 1e9 * 1e9`。

---

## 四、坑 2：移位位数 ≥ 类型宽度是 UB，编译期和运行时**结果不同**（实测）

同一个表达式，两种写法给出**两个不同的值**——这是 UB 的教科书式表现：

| 表达式 | 常量折叠（编译期）| `volatile` 运行时 | 为什么不一样 |
|---|---|---|---|
| `1 << 32` | **0** | **1** | x86 的 `shl` 指令只取移位数量的**低 5 位**：`32 & 31 = 0` → 等于 `1 << 0 = 1`；而编译器按标准折叠成 0 |
| `1LL << 64` | **0** | **1** | 低 6 位：`64 & 63 = 0` → `1LL << 0 = 1` |
| `1 << 40` | — | **256** | `40 & 31 = 8` → `1 << 8 = 256` |

**"同一份代码，两个结果"就是"这是 UB，行为不保证"的直接证据。** 别去记"32 会变成 1 还是 0"，正确答案是"不知道，也不能依赖"。

编译器的态度也很微妙（实测，`-O2 -Wall -Wextra -Wshift-overflow=2`）：

| 写法 | GCC 16.2 / C++17 的警告 |
|---|---|
| `1 << 32`、`1LL << 64`（移位数超宽）| ✅ `warning: left shift count >= width of type [-Wshift-count-overflow]` |
| **`1 << 31`、`1LL << 63`（只差一位的溢出）**| ❌ **一声不吭，完全没警告** |

> 也就是说：**编译器只帮你抓"移位数太宽"，抓不住"结果装不下"**。后者只能靠你自己的类型知识。

## 五、实际写码规则（这四条就够）

| 场景 | 写法 |
|---|---|
| n 确定很小（≤ 30）| `1 << n` 可以 |
| **只要 n 有可能 ≥ 31，或者要往 `long long` 里放** | **一律写 `1LL << n`**（多两个字符，零成本，永远不会错）|
| 枚举子集 `for (int m = 0; m < (1 << n); ++m)` | n ≥ 31 会得到错误/死循环；必须 `1LL << n` **且 mask 变量也用 `long long`** |
| 拿 2 的幂当 INF | 2²⁹ = 5.37e8 **不算"足够大"**，用 `0x3f3f3f3f` 或 `(ll)1e18` |

## 六、附：2ⁿ 量级表（决定"能不能枚举"）

| n | 2ⁿ | 机试里意味着什么 |
|---|---|---|
| 10 | 1,024 | 随便枚举 |
| 20 | 1,048,576（≈1e6）| 枚举的**舒适区** |
| **25** | 33,554,432（≈3.4e7）| **枚举的实际上限**（约 0.1~0.5s）|
| **29** | **536,870,912（≈5.4e8）** | **已经超时**（>1s）——注意这正是你问的那个数 |
| 30 | 1,073,741,824（≈1.1e9）| `int` 还能表示，但绝不能枚举 |
| 31 | 2,147,483,648（≈2.1e9）| `int` 表示不了 → 必须 `1LL << 31` |
| 40 | 1,099,511,627,776（≈1.1e12）| 只能 `long long` |
| 62 | 4,611,686,018,427,387,904 | `long long` 的极限 |
| 63 | 9,223,372,036,854,775,808 | 超出 `long long` → 变负 |

> ⚠️ 顺带一句：**"能表示"和"能枚举"是两件完全不同的事**。2²⁹ 在 `int` 里表示得好好的，但 5.4 亿次操作在机试 1s 限时里跑不完。位掩码题看到 n ≥ 26 就要立刻想别的做法（DP / 折半枚举 / 剪枝）。

## 七、自查（先做完再翻答案）

1. `long long x = 1 << 31;` 里 `x` 是多少？怎么改才对？
2. `1 << 30` 会溢出吗？`1 << 31` 呢？`1LL << 63` 呢？
3. `for (int m = 0; m < (1 << 31); ++m)` 会发生什么？
4. 为什么 `1LL << 63` 不能当"long long 里最大的数"？
5. 2²⁹ 次循环在机试里能跑吗？那 `1 << 29` 作为位掩码的规模现实吗？
6. `long long s = 1e9 * 1e9;` 结果对吗？为什么？

<details>
<summary>答案</summary>

1. `-2147483648`。`1 << 31` 先在 `int` 里溢出，再转 `long long`。改法：`1LL << 31`。
2. `1 << 30` = 1,073,741,824 **不溢出**（`INT_MAX` 是它的两倍减一）；`1 << 31` **溢出**（得到 `-2147483648`，UB）；`1LL << 63` **溢出**（得到 `LLONG_MIN = -9223372036854775808`）。合法上限分别是 `1 << 30` 和 `1LL << 62`。
3. `1 << 31` 是负数，`m < 负数` 一开始就为假 → **循环一次都不执行**（不是死循环，是"静默不做"）；如果写成 `1u << 31` 或 `1LL << 31`（2.1e9），就会跑 21 亿次 → **TLE 或直接卡死**。
4. 因为 `long long` 是有符号的，第 63 位是符号位：`1LL << 63` 正好把符号位顶成 1 → 等于 `LLONG_MIN`。最大的正数是 `LLONG_MAX` = `2⁶³ - 1` = `(1LL << 62) - 1 + (1LL << 62)`，或者说"最大的 2 的幂"是 `1LL << 62`。
5. 跑不完。5.4e8 次简单操作在 1s 限时下基本必 TLE（舒适区是 1e7~1e8 量级）。作为位掩码，`n = 29` 意味着 29 个元素的子集枚举——现实上限约 `n ≤ 25`。
6. 不对。`1e9` 是 `double`，`1e9 * 1e9` 是浮点乘法（结果 1e18，能表示）；但若写成 `int` 变量相乘（如 `int a = 1e9; long long s = a * a;`）就是 `int` 溢出。要写 `1LL * a * a`。
</details>
