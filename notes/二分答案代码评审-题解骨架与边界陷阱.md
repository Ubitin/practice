# 二分答案代码评审：题解骨架与边界陷阱（P1873 砍树）

> 触发点：拿两份代码来问"题解的代码是否存在逻辑错误"——
> ① 题解：`int L = 0, R = 1e9, ans, mid; while (L <= R) if (P(mid = L + R >> 1)) ans = mid, L = mid + 1; else R = mid - 1;`

**两边的二分骨架是等价的**——你也在条件里重新赋值了 `mid`，所以 `mid` 每轮都在更新。（如果哪一版写成 `if(p(v[mid], ...))` 而 `mid` 只在循环外算一次，那就必死循环；你现在这版没有这个问题。）

## 二、题解逐行评审

```cpp
int L = 0, R = 1e9, ans, mid;
while (L <= R)
    if (P(mid = L + R >> 1))          // 一种压行技巧
        ans = mid, L = mid + 1;
    else
        R = mid - 1;
```

### ✅ 第 1 关：`L + R >> 1` 的优先级 —— **正确**

这是最容易被误判为 bug 的地方。C++ 中**加法优先级高于移位**，所以：

```
L + R >> 1   ≡   (L + R) >> 1
```

**实测**：36 组 `(L, R)` 组合（含 0、7、999、10⁹、2³⁰）全部相等 ✔

**⚠️ 但 `-Wall` 会给你一个警告**（这是实测原文）：

```
warning: suggest parentheses around '+' inside '>>' [-Wparentheses]
   45 |         if (P(mid = L + R >> 1))
      |                     ~~^~~
```

> 编译器明确说"建议给 `+` 加括号"。**语义对不等于该这么写**——你刚学 C++ 时把优先级背错一次，这段代码就会读成 `L + (R >> 1)`，二分区间直接错一半，而且照样编译通过。**加个括号，零成本。**

### ✅ 第 2 关：闭区间二分写法 —— **正确**

`while (L <= R)` 配 `L = mid + 1` / `R = mid - 1` 是标准的**闭区间**写法，两个分支都让区间**严格缩小**：

- `L == R` 时 `mid == L == R` → 真则 `L = R+1 > R` 退出；假则 `R = L-1 < L` 退出。

**不会死循环。** ✔

### ✅ 第 3 关：单调性假设 —— **成立**

`P(H) = Σ max(0, hᵢ − H) ≥ M`，随 `H` 增大而**单调不增**（H 越高，砍到的木头越少）。"真在前、假在后"的单调结构正是二分答案的前提。取最后一个为真的 `H` = 最大可行锯片高度 ✔

### ✅ 第 4 关：对拍 —— **0 错**

本机 20000 组随机数据（保证有解，与暴力枚举逐组比对）：

```
题解 int 版       错 0 组
题解 ll  版       错 0 组
用户版 r=1e9      错 0 组
用户版 r=2e9      错 0 组
```

两组合法样例也都对：`4 7 / 20 15 10 17 → 15`、`5 20 / 4 42 40 26 45 → 36`。

## 三、题解的三处真实缺陷

### ★① `int ans, mid;` —— **`ans` 没有初值**（潜在 UB）

```cpp
int L = 0, R = 1e9, ans, mid;   // ← ans 未初始化
```

如果 `P` 在整个区间上都为假，`ans` 一次都不会被赋值，最后读它 → **未定义行为**（读到什么完全随机）。

**实测**：构造无解数据（树高总和 16，M = 100），跑 5000 组：

```
ans 从未被赋值：5000 / 5000 组
```

> **它为什么还能 AC？** 因为 P1873 的数据**保证 M ≤ 树高总和**，此时 `H = 0` 一定能满足（砍掉全部树），`ans` 必然被赋过值。
> **但这是"题目保证"救的，不是代码对。** 换个不保证有解的题（例如"若无法满足输出 −1"），这段代码直接炸。**自己写时就写 `long long ans = 0;`**，零成本。

### ★② `int` 与 `1e9` 混用 —— 本约束下安全，但贴边

| 项 | 情况 |
|---|---|
| `int R = 1e9;` | `1e9` 是 **double 字面量**，隐式转 `int`；值恰好为 1000000000，安全 |
| `L + R` | 循环内恒有 `L ≤ R ≤ 10⁹`，故 `L + R ≤ 2×10⁹ = 2000000000` |
| `INT_MAX` | **2147483647** |
| 结论 | `2×10⁹ < INT_MAX` → **本约束不溢出** ✔，但余量只有 **1.47×10⁸** |

> 记忆取整是求 `(L+R)/2`，很多人以为 `L+R` 不会超 `int`——**这里恰好没超，纯属运气好**。把上界从 `1e9` 提到 `2e9`（像你自己代码那样），`L+R` 到 `4×10⁹` 就**必然溢出**。所以：**二分答案一律用 `long long`**，别用 `int`。

### ★③ `scanf("%lld...")` 必须配 `long long` —— 图里看不到声明

题解片段里是 `scanf("%lld%lld", &n, &m);` 和 `scanf("%lld", &a[i]);`。`%lld` 要求 `long long*`：

- 若 `n`、`m`、`a[]` 声明为 `long long` ✅ 正确
- 若声明为 **`int`** ❌ → 传 `int*` 给 `%lld` 是**未定义行为**（典型症状：读到垃圾值、答案离谱）

> 图片里没显示这几个变量的声明，**抄题解时请务必一起核对**。安全写法：直接 `cin >> n >> m;`（类型由编译器检查，不会错）。

## 四、你自己的代码评审

当前 `01.cpp`：

```cpp
long long find(long long l, long long r){
    long long mid = (l + r) >> 1;      // ← 死代码：下面条件里会重新赋值
    long long ans = 0;                 // ← 有初值 ✔ 比题解稳
    while(l <= r){
        if(p(mid = (l + r) >> 1)){     // ← 每轮重新赋值 ✔
            ans = mid; l = mid + 1;
        }
        else r = mid - 1;
    }
    return ans;
}
```

**实测 8 个用例全部通过**：

| 用例 | 期望 | 实得 |
|---|---|---|
| `4 7` / `20 15 10 17` | 15 | **15** ✔ |
| `5 20` / `4 42 40 26 46` | 36 | **36** ✔ |
| `2 7` / `20 15`（答案 14 不在数组里） | 14 | **14** ✔ |
| `1 5` / `10` | 5 | **5** ✔ |
| `1 100` / `10`（无解） | 0 | **0** ✔ |
| `3 7` / `5 5 5` | 2 | **2** ✔ |
| `2 10` / `30 20` | 20 | **20** ✔ |
| `2 5` / `0 0` | 0 | **0** ✔ |

而且你比题解多做了三件对的事：

1. **`ans = 0` 有初值** → 无解时不 UB ✔
2. **全用 `long long`** → 没有 `int` 贴边风险 ✔
3. **`p()` 改成线性扫描、全局 `vector`** → 不依赖排序、不拷贝大数组 ✔（之前那版用 `upper_bound` 却没排序，是个大坑；现在这版没这个问题）
4. **二分的是值域 `[0, 2e9]`** → 避开了"答案必须是某个树高"的错误假定 ✔

### 两处可以清理的小事

**(1) 第 18 行是死代码**

```cpp
long long mid = (l + r) >> 1;   // 下面条件里立刻重新赋值，这行的值从未被用到
```
删掉即可。（留着也不出错，但会让读代码的人以为"mid 只算一次"——这正是我上一轮误判的原因。）

**(2) `r = 2e9` 偏大，但没有错**

树高 ≤ 10⁹，所以答案 ≤ 10⁹。`r = 2e9` 只是多跑一轮（31 轮 vs 30 轮），结果不受影响。想更紧凑可以写 `r = *max_element(v.begin(), v.end())` 或 `1e9`。

**(3) `p()` 可以加提前返回**

```cpp
bool p(long long x){
    long long sum = 0;
    for(int i = 0; i < n; ++i){
        if(v[i] > x){
            sum += v[i] - x;
            if(sum >= h) return true;   // 够用就走，省时间也防溢出
        }
    }
    return sum >= h;
}
```

## 五、⭐ 附：我自己在这次评审里踩的坑（值得记住）

第一次实测你的代码时，**8 个用例全部输出 `2000000000`**，也就是返回了初值 `r`。这与源码逻辑矛盾（我手算的轨迹明明收敛到 15）。

排查后发现：**是我的测试脚本错了。**

```powershell
function T($name, $input, $expect) {      # ❌ $input 是 PowerShell 保留自动变量
    $feed | & $exe
}
```

`$input` 在 PowerShell 里是**保留的自动变量**（代表管道输入的枚举器），把它当函数参数名会导致参数绑不上，程序**一个字符的输入都没收到**。于是：

```
n = 0, h = 0  →  p() 里循环一次都不执行  →  sum = 0
              →  return sum >= h  即  0 >= 0  →  恒真
              →  ans 每轮都被赋成 mid，l 一路爬到 r
              →  最终输出 r = 2000000000
```

改成 `$feed` 后，**8 个用例全部通过**。

> **教训：当"程序行为"与"代码逻辑"矛盾到无法解释时，先怀疑测试工具本身。**
> 尤其注意：`n = 0` 这类"输入没读到"的现象，在判定函数里常常退化成 `0 >= 0` 恒真，把 bug 伪装成"算法全错"。
> 我上一轮还差点因为同样的表象得出"你的代码是错的"这个结论——**这是必须避免的误判**。

## 六、二分答案骨架 + 三条铁律

```cpp
// 【求最大可行值】（P1873 这类）
long long L = 0, R = 上界, ans = 0;      // ⚠️ ans 一定要给初值
while (L <= R) {
    long long mid = (L + R) >> 1;        // ⚠️ 加括号；一律 long long
    if (P(mid)) { ans = mid; L = mid + 1; }
    else        { R = mid - 1; }
}
cout << ans;

// 【求最小可行值】
// long long L = 下界, R = 上界, ans = R;
// while (L <= R) { long long mid = (L+R)>>1;
//     if (P(mid)) { ans = mid; R = mid - 1; } else L = mid + 1; }
```

### ⚠️ 三条铁律

1. **`mid` 必须在循环体内计算。** 写在外面且不重新赋值 → 死循环。
2. **`ans` 必须给初值。** 否则无解时读它是 UB（题解这里就欠了）。
3. **二分域是"答案的取值范围"，不是数组下标。** 反例：`a={20,15}, M=7` → 答案 14，而 14 不在数组里（实测 95% 的随机数据都这样）。

## 七、自查

1. `L + R >> 1` 在 C++ 里怎么结合？为什么 `-Wall` 还要警告它？
2. 题解的 `int ans, mid;` 有什么问题？为什么它仍然能 AC？
3. 题解用 `int L, R` 而 `L + R` 最大到多少？离 `INT_MAX` 差多少？把你的上界改到 `2e9` 会怎样？
4. 你的代码第 18 行 `long long mid = (l + r) >> 1;` 是死代码，为什么？
5. 当测试结果与代码逻辑矛盾时，第一步应该怀疑什么？

**答案要点**
1. 加法优先级高于移位，等价于 `(L + R) >> 1`；但依赖优先级记忆容易看错/改错，编译器因此建议加括号（实测警告原文 `suggest parentheses around '+' inside '>>'`）。
2. `ans` 未初始化，`P` 全假时读它是未定义行为。P1873 保证 M ≤ 树高总和，此时 H=0 必可行，`ans` 必然被赋值——是题目保证救的，不是代码对（实测无解数据 5000/5000 组 `ans` 从未被赋值）。
3. `L + R ≤ 2×10⁹`，`INT_MAX = 2147483647`，余量只有 1.47×10⁸，不溢出。若上界提到 `2e9`，`L + R` 到 4×10⁹ → 必然 `int` 溢出，必须用 `long long`。
4. 因为条件 `p(mid = (l + r) >> 1)` 里的赋值会在每次循环开头把 `mid` 重新算一遍，第 18 行赋的值从未被读取。
5. 先怀疑**测试工具/测试脚本本身**。本次就是 PowerShell 的保留自动变量 `$input` 导致输入没喂进去，`n=0,h=0` 使 `0 >= 0` 恒真，伪装成"算法全错"。
