## 一、先确认：这是纯性能问题，不是 WA

用暴力 O(n²) 在 3000 组随机小数据上对拍（含大量重复值），三种正解全部 **0 组不一致**。而且关键一点：

> **`erase` 那套逻辑本身是正确的**——实测"不 erase 的写法"与你的"erase 写法"在 2000 组数据上答案完全一致。
> 所以**不要**去动逻辑，只动性能。

### ⭐ 铁证：数「元素拷贝次数」，不数耗时

第一版我用计时来论证，结果大 n 处出现**非单调**（n=8000 用 80.3ms、n=16000 只用 56.6ms）——这是缓存和内存分配器的噪声，不可靠。

**改用"数操作次数"就完全确定了**（构造：n/2 个 1 + n/2 个 2，C=1）：

| n | 拷贝元素总数 | **/n²** | erase 搬移 | **/n²** | fi 扫描次数 | **/n²** |
|---|---|---|---|---|---|---|
| 1000 | 1999000 | **2.00** | 499500 | **0.50** | 501000 | **0.50** |
| 2000 | 7998000 | **2.00** | 1999000 | **0.50** | 2002000 | **0.50** |
| 4000 | 31996000 | **2.00** | 7998000 | **0.50** | 8004000 | **0.50** |
| 8000 | 127992000 | **2.00** | 31996000 | **0.50** | 32008000 | **0.50** |
| 16000 | 511984000 | **2.00** | 127992000 | **0.50** | 128016000 | **0.50** |

三列的 `/n²` **全部是常数** → 三项都是严格的 O(n²)，没有任何一项是"小常数"。这比任何耗时曲线都有说服力。

**换算到本题上限 n = 2×10⁵**：

```
拷贝元素总数 2n² = 8.0 × 10^10 个 long long
               = 0.64 TB 的内存拷贝
最坏（两个 fi 都命中）3n² = 0.96 TB
```

> **光是 memcpy 就是 TB 量级。** TLE 是结构性的必然，跟"加个 inline""换编译器"这类常数优化毫无关系。

| n | 原版扫法 | 翻倍 | `upper_bound - lower_bound` | 翻倍 |
|---|---|---|---|---|

## 三、关键洞察：`erase` 和最后的 `/2` 都是多余的

题面说 **C 是正整数**，即 $C\ge 1$。于是：

$$A-B=C\ge 1 \;\Longrightarrow\; A>B \;\Longrightarrow\; \text{A 与 B 的值不同} \;\Longrightarrow\; \text{必然落在不同位置}$$

所以你根本不需要：
- ❌ `erase` 掉自己（自己不可能和自己配对）
- ❌ 同时从 A 侧和 B 侧各数一遍再 `/2`

**只需从一侧数**：排序后对每个 $B$，统计值 $B+C$ 出现了几次。每个合法数对恰好被数到一次。

> 实测确认：不 erase 的写法与原版在 2000 组数据上答案**完全一致**。

## 四、三种正解 + 实测耗时（n = 2×10⁵）

### 方案 A：排序 + 二分（推荐，最不容易写错）

```cpp
sort(a.begin(), a.end());
ll ans = 0;
for (ll i = 0; i < n; ++i) {
    ll t = a[i] + C;
    ans += upper_bound(a.begin(), a.end(), t)
         - lower_bound(a.begin(), a.end(), t);
}
cout << ans;
```

**复杂度 O(n log n)。**

### 方案 B：排序 + 双指针（尺取法）—— 常数最小

```cpp
sort(a.begin(), a.end());
ll ans = 0, j = 0, k = 0;
for (ll i = 0; i < n; ++i) {
    ll t = a[i] + C;
    if (j < i) j = i;
    if (k < i) k = i;
    while (j < n && a[j] <  t) ++j;   // j = 第一个 >= t
    while (k < n && a[k] <= t) ++k;   // k = 第一个 >  t
    ans += k - j;                     // [j, k) 全是 t
}
```

**排序 O(n log n) + 扫描 O(n)。**

### 方案 C：哈希计数 —— 值域大时最快

```cpp
unordered_map<ll, ll> cnt;
cnt.reserve(n * 2);                   // 防 rehash
for (ll x : a) cnt[x]++;
ll ans = 0;
for (auto& p : cnt) {
    auto it = cnt.find(p.first + C);  // ⚠️ 必须 find，不能写 cnt[p.first + C]
    if (it != cnt.end()) ans += p.second * it->second;
}
```

**期望 O(n)。**

### 实测（n = 200000）

| 方案 | 随机数据（值域 1e9） | 极端重复（值域 3 个） |
|---|---|---|
| A 二分 | 17.89 ms | 5.95 ms |
| **B 双指针** | **8.94 ms** | 2.43 ms |
| C 哈希 | 25.95 ms | **1.09 ms** |

三种都远在 1 秒限制内（最快 1 ms，最慢 26 ms）。选哪个都行：
- **追求稳妥** → 方案 A（不易写错，双 log 也够快）
- **追求最快** → 方案 B（常数最小）
- **值域特别大 / 讨厌写边界** → 方案 C

## 五、通用经验：怎么在提交前发现 O(n²)

### 1. 看循环里有没有"整容器拷贝"

```cpp
vector<int> u = v;        // ❌ 在循环里 = O(n²) 起步
vector<int> u = std::move(v);  // 也要小心
```
**一条通则：循环体内出现"按值传递容器"或"整容器赋值"，先怀疑 O(n²)。**

### 2. 看函数形参是不是按值传递

```cpp
ll fi(ll x, vector<ll> v)          // ❌ 每次调用都拷贝 O(n)
ll fi(ll x, const vector<ll>& v)   // ✅ 零拷贝
```
**容器做参数，一律 `const&`**（除非确实需要副本）。

### 3. 看是不是"自己扫区间"代替了二分

```cpp
// ❌ 统计值 x 的出现次数：O(出现次数)
auto it = lower_bound(...); for (...) if (*it != x) break; sum++;

// ✅ O(log n)
sum = upper_bound(v.begin(), v.end(), x) - lower_bound(v.begin(), v.end(), x);
```

### 4. 算一下最坏情况的操作次数

本题：n = 2×10⁵ → n² = 4×10¹⁰，已经远超 1 秒能做的约 10⁸ 次操作。**看到 n² 与 n=2×10⁵ 直接就该警觉。**

### 5. ⭐ 论证复杂度优先"数操作次数"，别只靠计时

这次实测的直接教训：**计时在大 n 处被缓存和内存分配器的噪声污染，出现了"n 越大反而越快"的假象**（80.3ms → 56.6ms）。而数操作次数是**确定性**的，`/n²` 恒为 2.00 一目了然。

> **方法论：怀疑复杂度时，插一个计数器数关键操作，比看秒表可靠得多。**

## 六、坑清单

| # | 坑 | 后果 |
|---|---|---|
| 1 | 循环里 `vector<ll> u = v;` | O(n²) 起步，本题主因 |
| 2 | 容器形参按值传递 | 每次调用 O(n) 拷贝，隐蔽性极强 |
| 3 | 用 `erase` 中间元素 | O(n) 搬移；且本题根本不需要 |
| 4 | 自己 `for` 扫区间统计出现次数 | O(出现次数)，应换 `upper-lower` |
| 5 | 双计数后 `/2` | 白做一倍工作；C ≥ 1 时完全不必 |
| 6 | 只凭计时判断复杂度 | 缓存/分配器噪声会给出错误结论（本次实测踩到） |
| 7 | `cnt[p.first + C]` | `operator[]` 会**插入**新键：`unordered_map` 触发 rehash → 迭代器失效 UB；`map` 边遍历边插入 → 死循环 |
| 8 | 忘记 `cnt.reserve()` | 大量 rehash，哈希方案可能比二分还慢 |
| 9 | `a[i] + C` 用 `int` | 可能溢出（值可达 2³⁰），用 `long long` |
| 10 | 答案用 `int` | 最多约 n²/4 个数对，n=2×10⁵ 时远超 `int` 范围，必须 `long long` |

## 七、自查

1. 你的代码里有几处 O(n²)？分别在哪一行？为什么 `fi` 的**形参写法**也是其中之一？
2. 为什么这题**不需要** `erase` 自己、也**不需要**最后 `/2`？这依赖题面的哪个条件？
3. 统计一个值在有序数组里出现几次，最规范的写法是什么？复杂度多少？为什么不要自己 `for` 扫？
4. 如果只靠计时来判断复杂度，什么情况下会被误导？更可靠的替代做法是什么？
5. 为什么 `unordered_map` 里写 `cnt[p.first + C]` 是危险的？

**答案要点**
1. 三处：`u = v`（O(n)/次 × n）、`u.erase`（O(n)/次 × n）、`fi` 形参 `vector<ll> v` 传值（每次调用 O(n)，约调用 n 次）。另外 `fi` 内部自扫区间是第四层。
2. 因为题面 C 是正整数，$A-B=C\ge1$ 蕴含 $A>B$，两者值不同、必然在不同位置，所以不会配到自己，也不需要两遍计数再平均。
3. `upper_bound(v,x) - lower_bound(v,x)`，O(log n)。自己 `for` 扫是 O(出现次数)，实测 n=16000 时慢约 196 倍。
4. 缓存、内存分配器、缺页、CPU 频率都会污染计时——本次就出现"n 从 8000 翻到 16000，耗时反而从 80.3ms 降到 56.6ms"。替代做法：插计数器数"关键操作次数"，看它除以 n² 是不是常数。
5. `operator[]` 在键不存在时会**插入**新元素。对 `unordered_map` 可能触发 rehash，使当前遍历用的迭代器失效（UB）；对 `map` 则是一边遍历一边加元素，可能永远走不完。必须用 `find`。
