# 如何写对拍程序（C++ 版）

> 触发点：想知道怎么系统地写对拍，把"样例过了但 WA"这类问题在本地揪出来。
> 一句话：对拍 = **数据生成器 + 待测解 + 暴力解**，写个 C++ 小程序循环"造数据 → 两边各跑一次 → 比输出"，不一致就把数据存下来。
> 配套代码：`test_\stress_cmp.cpp`（对拍器）、`test_\stress_gen.cpp`（生成器模板）、`test_\01_cf1486d_brute.cpp`（暴力解示例）、`test_\01_cf1486d_wrong.cpp`（错误解示例）。
> 相关：`随机数生成详解`（生成器里的随机数技巧）、`公共核心讲义` §调试三板斧。

## 一、对拍为什么有效

人工造数据的问题是：**你只会想到自己已经想到的情况**。而 bug 恰恰藏在你没想到的地方。

对拍把这件事自动化了：让程序去碰几千几万组数据，只在"两个程序答案不一样"时才叫你。**它把"找反例"从人的直觉变成了机器的穷举。**

你之前遇到的问题几乎都能被它抓住：

| 曾经的 bug | 对拍能否抓到 |
|---|---|
| Havesine 角度没转弧度（错 51%） | ✅ 立刻 |
| P1824 变量遮蔽崩溃 | ✅ 立刻（RE 检测） |
| P2440 整数除零（只在答案=1 时） | ✅ 需要边界风格的数据 |
| CF1486D 把"子段中位数"做成"全局第 t 大" | ✅ 第 4 轮就抓到 |
| P1024 漏根（二分后没输出） | ✅ 立刻 |

## 二、标准三件套

| 角色 | 作用 | 要求 |
|---|---|---|
| **`gen`** 生成器 | 造随机数据到 `stdout` | 规模要小（暴力才跑得动）；**必须覆盖边界**；种子从命令行传入 |
| **`sol`** 待测解 | 你正在调的那份代码 | 就是它 |
| **`brute`** 暴力解 | 保证正确但很慢 | **必须真的正确**；否则对拍毫无意义 |

对拍器循环：

```
for t in 1..N:
    gen t > in.txt          # 用 t 当种子，可复现
    sol   < in.txt > out_sol.txt
    brute < in.txt > out_brute.txt
    if out_sol != out_brute:  保存数据、报错、停下
```

## 三、生成器怎么写

### 3.1 种子必须从命令行传入

```cpp
int main(int argc, char** argv) {
    unsigned seed = (argc > 1) ? (unsigned)stoul(argv[1])
                               : (unsigned)chrono::steady_clock::now().time_since_epoch().count();
    mt19937 rng(seed);
    ...
}
```

- 对拍器传 `1, 2, 3, ...` 当种子 → **每组数据都不同**
- 但**同一个种子永远生成同一份数据** → 复现 bug 时直接 `gen.exe 4 > in.txt` 就能重放

> ⚠️ 别用 `time(0)` 当种子：同一秒内多次启动会得到**完全相同**的数据（`随机数生成详解` 里实测过这个坑）。

### 3.2 ⭐ 风格轮换：让边界数据一定会被生成

**纯随机会漏掉边界**，这是对拍最常见的"假通过"来源。用 `seed % K` 强制轮换：

```cpp
int style = (int)(seed % 4);
switch (style) {
    case 0:              // 纯随机
        for (auto& x : a) x = 1 + rng() % n;   break;
    case 1:              // 全部相同  ← 最容易被忽略
        { int v = 1 + rng() % n; for (auto& x : a) x = v; }  break;
    case 2:              // 严格递增  ← 让"全局次序统计量"类错法蒙对
        for (int i = 0; i < n; ++i) a[i] = i + 1;           break;
    case 3:              // 只有两种值（大量重复）
        for (auto& x : a) x = (rng() % 2) ? 1 : n;           break;
}
```

**本机实测**（`stress_gen.exe 1..8`）：

```
seed=1 : 2 2 / 1 1
seed=2 : 1 1 / 1
seed=3 : 11 9 / 1 1 11 11 11 1 1 1 11 1 1     ← 两种值
seed=4 : 11 2 / 9 3 5 4 1 11 7 2 4 9 11       ← 纯随机
seed=5 : 12 7 / 8 8 8 8 8 8 8 8 8 8 8 8       ← 全相同
seed=6 : 3 1 / 1 2 3                          ← 严格递增
```

**要覆盖的边界清单**（按题型挑）：
- 最小值规模：`n = 1`、`n = 2`、`k = 1`、`k = n`
- 全相同值 / 全部递增 / 全部递减 / 只有两种值
- 极值：值域上下界
- 特殊结构：所有元素都能配对、答案恰好是 0 或 1

### 3.3 输出格式必须与题面**逐字一致**

生成器输出的格式错了，两个解都会读错，对拍结果就没意义。写完生成器**先手动看一眼**：

```powershell
.\stress_gen.exe 4
```

## 四、C++ 对拍器的核心：进程控制

### 4.1 为什么不能只用 `system()`

最简单的写法是：

```cpp
system("gen.exe 1 > in.txt");
system("sol.exe < in.txt > out_sol.txt");
system("brute.exe < in.txt > out_brute.txt");
```

**问题：`system()` 会一直阻塞。**待测解一旦死循环，对拍器自己就**永久挂住**了——而你恰恰最想测出死循环。

### 4.2 正确做法：`CreateProcess` + 超时强杀

```cpp
HANDLE hIn  = CreateFileA("stress_in.txt",  GENERIC_READ,  FILE_SHARE_READ, &sa, OPEN_EXISTING, ...);
HANDLE hOut = CreateFileA("stress_sol.txt", GENERIC_WRITE, FILE_SHARE_READ, &sa, CREATE_ALWAYS,  ...);

STARTUPINFOA si{};
si.dwFlags    = STARTF_USESTDHANDLES;
si.hStdInput  = hIn;          // 重定向 stdin
si.hStdOutput = hOut;         // 重定向 stdout
si.hStdError  = GetStdHandle(STD_ERROR_HANDLE);

PROCESS_INFORMATION pi{};
CreateProcessA(NULL, cmdline, NULL, NULL, TRUE, CREATE_NO_WINDOW, NULL, NULL, &si, &pi);

DWORD wr = WaitForSingleObject(pi.hProcess, timeoutMs);   // ★ 带超时地等
if (wr == WAIT_TIMEOUT) {
    TerminateProcess(pi.hProcess, 1);                     // ★ 超时强杀 → 能测出 TLE
} else {
    DWORD ec; GetExitCodeProcess(pi.hProcess, &ec);       // ★ 拿退出码 → 能测出 RE
}
```

**四个关键点**：

1. `SECURITY_ATTRIBUTES.bInheritHandle = TRUE` —— 句柄必须可继承，否则子进程拿不到
2. `STARTF_USESTDHANDLES` + 三个 `hStd*` —— 用文件句柄代替管道，避免 I/O 瓶颈
3. `WaitForSingleObject` 的第二个参数是**超时毫秒数** —— 这是 `system()` 做不到的
4. `GetExitCodeProcess` —— 拿到退出码就能区分"正常结束"和"崩溃"

> `CREATE_NO_WINDOW` 只是为了不弹出黑框，与功能无关。

### 4.3 输出比较：必须归一化

**Windows 的换行是 `\r\n`，Linux 是 `\n`**，而且末尾多一个换行、行尾多几个空格都很常见——不归一化会制造**假报错**。

```cpp
static string normalize(const string& s, bool ignoreWs) {
    if (ignoreWs) {                       // --ws：忽略所有空白
        string r;
        for (char c : s) if (!isspace((unsigned char)c)) r += c;
        return r;
    }
    // 默认：丢掉 '\r'、去掉行尾空白、去掉末尾空行
    ...
}
```

**两级策略**：
- **默认**：忽略 `\r` + 行尾空白 + 末尾空行（能挡掉绝大多数假报错，又不会漏掉真实的空格差异）
- **`--ws`**：完全忽略所有空白（**多选题**、或题目明确说"格式不限"时用）

> ⚠️ 别一上来就 `--ws`：它会把"少输出一个空格"这种真错也一起放过。

### 4.4 出错时必须保存数据

```cpp
cp("stress_in.txt",  "bad_in.txt");
cp("stress_sol.txt", "bad_sol.txt");
cp("stress_bru.txt", "bad_bru.txt");
```

**这是对拍器最有价值的功能**——否则你只知道"不一致"，却不知道在哪组数据上。存下来后：

```powershell
.\bad_sol.exe < bad_in.txt      # 直接复现
```

## 五、四类结果要分开报

对拍器不该只报"不一致"，**四类问题的排查方向完全不同**：

| 检测到 | 含义 | 该查什么 |
|---|---|---|
| **不一致** | 两个程序答案不同 | 至少有一个错。先确认暴力解对不对 |
| **RE**（退出码非 0） | 待测解崩溃 | 看退出码（`0xC0000005` 越界 / `0xC0000094` 除零…） |
| **TLE**（超时被杀） | 死循环或太慢 | 查循环边界；小数据还超时基本是死循环 |
| **暴力解自己也崩** | 对拍的前提没了 | **先修暴力解**，否则比出来的结论都不可信 |

> 我的对拍器在第 4 类上的处理是：**直接中止并提示"先修暴力解"**。因为暴力解错了，它给出的"正确答案"就是错的，后面所有比较都没有意义。

## 六、实战演示（CF1486D）

### 6.1 正确解 vs 暴力：300 轮全过

```
[对拍] 轮数 300，单次超时 3000 ms，比较模式 忽略行尾空白
  ...已通过 100 轮
  ...已通过 200 轮
  ...已通过 300 轮

[对拍] 300 轮全部通过 ✅
       不一致 0、RE 0、TLE 0、生成器异常 0
       待测解单次最慢 104.2 ms（超时阈值 3000 ms）
```

> ⚠️ **这 104.2 ms 不是算法耗时**，而是 `CreateProcess` 创建进程 + 加载 exe 的开销。**对拍器的计时只能用来发现"小数据也跑很久"（死循环），不能当作性能指标。** 真测性能要用大数据的单独计时（见 `CF1805C` 那篇的 `time` 模式）。

### 6.2 错误解 vs 暴力：**第 4 轮就抓到**

```
[第 4 轮] ✗ 输出不一致
  行数：sol=1  brute=1
  第 1 行不同：
    sol   = 11
    brute = 9
  → 已存 bad_in.txt / bad_sol.txt / bad_bru.txt
  数据（前 400 字符）：
----
11 2
9 3 5 4 1 11 7 2 4 9 11
----
```

**手算核对**：`k=2`，取长度 ≥ 2 的子段。
- 长度 2 的下中位数 = 两者较小值。最优是 `[9,11]`（末尾两个）→ **9**
- 长度 3 的下中位数 = 第 2 小。`[4,9,11]` → 9
- 想拿 11？需要某个子段里至少有 2 个 11（长度 2 要 2 个；长度 3 也要 2 个），而两个 11 之间隔着 4 个元素 → **拿不到**

所以正确答案是 **9**，错误解输出 11。

> 就这么 11 个数、4 轮，对拍就把"思路完全错位"这个根本性问题揪出来了——**如果靠手造数据，你多半会造出 `1 2 3 4 5` 这种"恰好蒙对"的例子。**

### 6.3 TLE / RE 也测出来了

```
⑤ RE 检测（整数除零）
[第 1 轮] ★ RE：退出码 -1073741676 (0xC0000094)

④ TLE 检测（死循环，超时设 1500ms）
[第 1 轮] ★ TLE：超过 1500 ms 被强杀
```

`0xC0000094` 正是整数除零——和 `整数除零导致RE-P2440木材加工排错` 那篇里遇到的完全一样。**对拍器直接把它标出来了。**

## 七、让对拍更有效的 7 个技巧

**① 数据规模要小。** 暴力解是 `O(n³)` 甚至指数级，`n` 只能开到 8~15。**规模小 ≠ 测不出**——绝大多数逻辑错误在小数据上就已经暴露。

**② 边界风格必须轮换。** 见 §3.2。这是"对拍通过了却还是 WA"的头号原因。

**③ 小数据可以全枚举，比随机更彻底。**
比如输入只有 `(a, b, c)` 三个 1~12 的整数，那就**穷举所有组合**（你之前的 `cmp01.py` 就是这么做的：`combinations(range(1,13), 3)`）。**穷举过 100% 的小案例，比随机跑一万次更让人放心。**

**④ 先验证暴力解自己。** 用一个更笨的方法（比如 Python 大整数、或把中间过程手工算一遍）抽查几组，确认暴力解的答案对。**暴力解错了，对拍就是在比两个错的东西。**

**⑤ 多选题要写"判题器"（checker），不要逐字比。**
如果 YES 时可以输出任意合法方案，两个正确程序的输出本来就不一样。这时候要校验"是否满足题目约束"，而不是比字符串。你之前的 `cmp1805c.py` 就做了这件事（校验输出的 k 确实在输入里且满足 `(b−k)² < 4ac`）。

**⑥ 出错就停下，把数据存好。**
第一组反例最有价值。存成 `bad_in.txt` 后可以反复复现、加打印、单步调。

**⑦ 记住"对拍通过 ≠ 没错"。** 它只能证明"在你生成的这批数据上没错"：
- 数据规模太小，溢出类 bug 测不出（要 `long long` 溢出的得把值开到 1e9）
- 数据风格没覆盖到的结构测不出
- 需要"最坏情况复杂度"的 TLE 测不出

## 八、对拍的局限

| 测不出来的东西 | 怎么办 |
|---|---|
| **TLE**（大数据才慢） | 单独写大数据计时：`gen.exe big` 造 `n=1e5` 数据，`Measure-Command` 计时 |
| **溢出**（值域不够大） | 生成器里专门开一档大值数据 |
| **需要特定结构的 hack 数据** | 手写构造（如"全是同一个数"、"答案恰好在边界"） |
| **浮点精度** | 用 `--ws`/容差比较，或写带 `eps` 的判题器 |
| **多解题** | 写 checker |

## 九、坑清单

| # | 坑 | 后果 |
|---|---|---|
| 1 | 用 `system()` 跑子进程 | 待测解死循环时**对拍器自己永久挂住**；用 `CreateProcess` + 超时强杀 |
| 2 | 比较前不归一化 | Windows `\r\n` / 行尾空格 / 末尾空行 → **假报错**，白白排查半天 |
| 3 | 一上来就 `--ws` 忽略所有空白 | 把"少输出一个空格"这类真错也放过了 |
| 4 | 生成器只写纯随机 | 边界数据永远测不到 → **"对拍 1000 组通过"却没有意义** |
| 5 | 用 `time(0)` 当种子 | 同一秒启动的多次运行数据完全一样 |
| 6 | 生成器输出格式与题面不一致 | 两个解都读错，比较结果无意义 |
| 7 | 暴力解本身有 bug | 拿它当裁判 → 越对越错 |
| 8 | 不保存出错数据 | 只知道"不一致"，无法复现和定位 |
| 9 | 把对拍器的耗时当性能指标 | 里面含 `CreateProcess` 开销（实测 100ms 量级），会严重误判 |
| 10 | 多选题逐字比较 | 两个正确解互相"打架"，永远对拍不过 |
| 11 | 数据规模开太大 | 暴力解跑不动，一轮几秒钟，对拍效率极低 |
| 12 | `CreateFileA` 忘了 `bInheritHandle = TRUE` | 子进程拿不到重定向的句柄，stdin/stdout 失效 |

## 十、自查

1. 对拍的三个角色分别是什么？各自有什么硬性要求？
2. 为什么对拍器要用 `CreateProcess` 而不是 `system()`？
3. 生成器里为什么要把"全相同 / 递增 / 只有两种值"这些风格轮着生成？
4. 比较输出前要做哪些归一化？为什么需要？
5. 对拍器报"不一致"时，第一步应该怀疑什么？
6. 为什么"对拍 1000 轮全过"仍然不能保证提交就能 AC？
7. 对拍器报出的"最慢 104.2 ms"能当算法性能看吗？为什么？

**答案要点**
1. `gen`（生成器，规模小、覆盖边界、种子从命令行传）、`sol`（待测解）、`brute`（暴力解，**必须真的正确**）。三者缺一不可。
2. `system()` 会一直阻塞：待测解死循环时对拍器自己就挂死了，而"测死循环"正是对拍最需要的能力。`CreateProcess` + `WaitForSingleObject(timeout)` + `TerminateProcess` 可以带超时地等并强杀。
3. 纯随机会漏掉边界结构，而对拍最常见的失败模式就是"随机数据全过、边界数据一提交就错"。用 `seed % K` 强制轮换能保证这些结构一定被生成到。
4. 至少要去掉 `\r`（Windows 换行）、行尾空白、末尾空行；必要时（多选题）忽略全部空白。不做归一化会制造假报错。
5. 先怀疑**暴力解**和**生成器**，再怀疑待测解。暴力解错了，"正确答案"就是错的，比较没有意义。
6. 因为对拍只覆盖了"生成器能造出的数据"。TLE（大数据才慢）、溢出（值域不够大）、需要特定结构的 hack 数据、浮点精度都可能测不出来。
7. 不能。它包含 `CreateProcess` 创建进程 + 加载 exe 的开销（实测 100ms 量级）。对拍器的计时只适合发现"小数据也跑很久"的死循环；真测性能要另写大数据计时。

## 附录：完整用法

**编译**（四个程序 + 对拍器）：

```powershell
g++ -std=gnu++17 -O2 stress_gen.cpp       -o stress_gen.exe
g++ -std=gnu++17 -O2 01_cf1486d_brute.cpp -o cf_brute.exe
g++ -std=gnu++17 -O2 01_cf1486d_fixed.cpp -o cf_fixed.exe
g++ -std=gnu++17 -O2 stress_cmp.cpp       -o stress_cmp.exe
```

**对拍**：

```powershell
.\stress_cmp.exe .\stress_gen.exe .\cf_fixed.exe .\cf_brute.exe 300 3000
#                  生成器            待测解          暴力解        轮数 超时ms
```

**换到别的题**：只改 `stress_gen.cpp` 的 `genCase()` 和 `brute.cpp`，对拍器本身不用动。

**实测输出汇总**

```
① 生成器四种风格轮换            → 见 §3.2
② 正确解 vs 暴力 300 轮         → 全部通过 ✅（最慢 104.2 ms）
③ 错误解 vs 暴力                → 第 4 轮抓到反例：11 2 / 9 3 5 4 1 11 7 2 4 9 11
                                  错误解 11，正确 9
④ 死循环解（超时 1500ms）        → 第 1 轮 ★ TLE，强杀，退出码 5
⑤ 整数除零解                    → 第 1 轮 ★ RE，退出码 -1073741676 (0xC0000094)，退出码 6
```

**对拍器的退出码约定**（方便脚本判断）：

| 退出码 | 含义 |
|---|---|
| 0 | 全部通过 |
| 1 | 参数错误 |
| 2 | 生成器连续异常 |
| 3 | 暴力解异常（先修它） |
| 4 | 待测解无法启动 |
| 5 | 待测解 TLE |
| 6 | 待测解 RE |
| 7 | 输出不一致 |
