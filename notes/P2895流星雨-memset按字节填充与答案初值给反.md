# P2895 流星雨 · 为什么"思路一致"却是 WA：memset 按字节填 + 答案初值给反

## 三、Bug 1：`memset` 是按字节填，不是按元素填

```cpp
memset(ti, -1, sizeof(ti));     // ✔ 对的
memset(b, 1002, sizeof(b));     // ✘ 这一行是元凶（b 是 long long[310][310]）
```

`memset(p, v, n)` 的语义是：**把从 p 开始的 n 个字节，每个字节都写成 `(unsigned char)v`**。它不认识你的元素类型。

| 调用 | 每字节被填成 | 8 个字节拼起来（long long） | 结果 |
|---|---|---|---|
| `memset(p, 0, n)` | `0x00` | `0x0000000000000000` | 0 ✔ |
| `memset(p, -1, n)` | `0xFF` | `0xFFFFFFFFFFFFFFFF` | -1 ✔（所以 `ti` 没事）|
| `memset(p, 0x3f, n)` | `0x3F` | `0x3F3F3F3F3F3F3F3F` | 4557430888798830399 ✔（可当 INF）|
| `memset(p, 1002, n)` | **`0xEA`** = 1002&0xFF | `0xEAEAEAEAEAEAEAEA` | **-1519143629599610134** ✘ |

`test_\memset_ll_demo.cpp` 的真实输出：

```
long long b[0][0] = -1519143629599610134
  b[0][0] == 1002 ? 否
  b[0][0] > 0      ? 否
  min(5, b[0][0])  = -1519143629599610134  <- 我想记录陨石时刻 5
  (0+1) >= b[0][1] ? 是  <- 会被当成"已经炸了"
int       c[0][0] = -353703190
  c[0][0] == 1002 ? 否
memset(d,-1) -> d[0][0] = -1  (正确)
```

**三重连锁反应**（这才是为什么"看着像算法全错"）：

1. `b[x][y] = min(t, b[x][y])` = `min(2, -1.5e18)` = **-1.5e18** ⇒ **陨石时刻根本没记进去**，`b` 里全是负数。
2. BFS 判据 `(t+1) >= b[nx][ny]` ⇒ `1 >= -1.5e18` **恒真** ⇒ 每个方向都 `continue` ⇒ **一步走不出去**。
3. 收尾判据 `b[i][j] == 1002` ⇒ **永假** ⇒ 一个安全格都统计不到。

正确写法（四选一）：

```cpp
const ll INF = (ll)1e18;

// ① 双循环：最直白
for (ll i = 0; i < 310; ++i)
    for (ll j = 0; j < 310; ++j) b[i][j] = INF;

// ② fill 摊平：二维数组内存连续，可以当一维用
fill(&b[0][0], &b[0][0] + 310 * 310, INF);

// ③ 把 b 定义成 int，就可以用 memset 0x3f（每个 int 正好 4 个字节，整字节重复）
int b[310][310];
memset(b, 0x3f, sizeof(b));      // 0x3f3f3f3f = 1061109567，远大于 t ≤ 1000

// ④ 用"题面上限 + 1"当哨兵（本题 t ≤ 1000，所以 1001/1002 够用）——同样要循环赋值
```

> ⚠️ **口诀：只有 0、-1、0x3f、0x7f 这种"每个字节都一样"的值能用 memset 填；其它数值一律循环或 fill。**
> ⚠️ "没被砸"的判据请写**区间** `b[i][j] > 1000`，不要写 `b[i][j] == 1002`——哨兵值哪天改成 1e9 或 INT_MAX，等号判断就又断了（教材写的就是 `death[i][j] > 1000`）。
> ⚠️ 元素是 `string`/`vector` 时绝不 memset（会破坏内部指针）。
> 手册已同步：**§2.6** 新增"第二个翻车点"实测段。

## 四、Bug 2：求最小值，`ans` 却从 0 开始

```cpp
ll ans = 0;                       // ← 求 min 却给了"最小可能值"
for (...) if (b[i][j] == 1002 && ti[i][j] != -1)
        ans = min(ans, ti[i][j]); // ti ≥ 0 ⇒ min(0, x) 永远是 0
if (ans == 1002) cout << -1;      // ← 判无解的哨兵和初值对不上，永不成立
else cout << ans;
```

实测：300 组随机数据里 **输出 0 的有 300 组（100%）**；样本期望 5、它输出 0。第 3 个 bug 是前两个的"合谋"：`ans` 恒为 0，`-1` 分支永远走不到。

**"最值三件套"必须成对**（初值 / 更新 / 判无解）：

| 目标 | 初值 | 更新 | 判"没更新过/无解" |
|---|---|---|---|
| 最小值 | `INF`（很大）| `ans = min(ans, x)` | `ans == INF` |
| 最大值 | `-INF`（很小）| `ans = max(ans, x)` | `ans == -INF` |
| 计数 | 0 | `++ans` | —— |

这与之前 `P1873` 那道题的 `int ans, mid` **未初始化**是同一族病：一个是**没给初值**、一个是**给反了初值**，共同点都是"样例能过（或恰好输出 0 看着不刺眼）、评测全错"。
手册已同步：**§6.6** 新增 ④ 三件套。

## 五、三处"看着像 bug、其实你写对了"

| 位置 | 你的写法 | 判定 |
|---|---|---|
| 能否站上去 | `(t+1) >= b[nx][ny]` → continue | ✔ 必须**严格早于**摧毁时刻。写成 `>` 就允许 `t+1 == b` —— "站在正在被砸的格子上" |
| 是否来过 | `ti[nx][ny] != -1`，在**入队时**判 | ✔ 入队即标记，队列不会暴涨（BFS 头号 bug 你没犯）|
| 陨石落点判负 | 落点没判负、邻居判了 | ✔ 题面保证 0 ≤ Xi,Yi ≤ 300，落点不必判；邻居**必须**判（教材的 `MIN` 宏就是干这个）|
| 数组上界 | 只判 `nx < 0 \|\| ny < 0` | ⚠️ 隐患：BFS 能一路铺到 x=309，下一次就会去读写 `b[310][ny]`（越界）。教材同样漏了。建议补 `nx >= 310 \|\| ny >= 310` |
| 安全格判据 | `b[i][j] == 1002` | ⚠️ 改成 `> 1000`（见 §三）|
| 循环变量 | 外层 `for(ll i…)` 里又嵌 `for(ll i…)` | ⚠️ `-Wshadow` 会点出来（实测原文 `declaration of 'i' shadows a previous local`）。本题**无害**（内层作用域独立、外层 `i` 不受影响），但 **P1824 那次 RE 就是变量遮蔽造成的**，别养成习惯 |

> **编译器不会救这两处**（实测）：`-Wall -Wextra` 对 `memset` 填错值和 `ans` 初值给反**一声不吭**（你的原码零警告）；加上 `-Wshadow` 也只抓到那个**无害**的 `i` 遮蔽。换句话说——**这类 bug 编译器、样例、肉眼全都放行，只有"自己对一遍初始化"和"对拍"能抓**。

## 七、修正版代码（`test_\01_p2895_fixed.cpp`，结构与你原码一致）

```cpp
#include <bits/stdc++.h>
using namespace std;
using ll = long long;

const ll INF = (ll)1e18;         // ★1 真正的"无穷大"

ll m = 0;
ll rm[4][2] = {{1,0},{0,1},{-1,0},{0,-1}};
ll b[310][310];      // 每个格子被摧毁的时间
ll ti[310][310];     // 走到每个格子的最早时间，-1 = 不可达

struct dot { ll x, y; };

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    memset(ti, -1, sizeof(ti));          // -1 整字节重复，合法
    for (ll i = 0; i < 310; ++i)         // ★2 不能用 memset(b,1002,sizeof(b))
        for (ll j = 0; j < 310; ++j) b[i][j] = INF;

    cin >> m;
    for (ll k = 0; k < m; ++k) {
        ll x, y, t; cin >> x >> y >> t;
        if (x >= 0 && y >= 0) b[x][y] = min(t, b[x][y]);   // ★3 落点也判负（防御式）
        for (ll d = 0; d < 4; ++d) {
            ll xt = x + rm[d][0], yt = y + rm[d][1];
            if (xt >= 0 && yt >= 0) b[xt][yt] = min(t, b[xt][yt]);
        }
    }

#define STRICT_START 0    // ★4 想严格处理"起点 0 时刻被砸"就改成 1（见 §五）
#if STRICT_START
    if (b[0][0] == 0) { cout << -1; return 0; }
#endif

    queue<dot> q;
    q.push({0, 0});
    ti[0][0] = 0;
    while (!q.empty()) {
        dot u = q.front(); q.pop();
        ll ux = u.x, uy = u.y, t = ti[ux][uy];
        for (ll d = 0; d < 4; ++d) {
            ll nx = ux + rm[d][0], ny = uy + rm[d][1];
            if (nx < 0 || ny < 0 || nx >= 310 || ny >= 310) continue;  // ★5 上下界都判
            if (ti[nx][ny] != -1) continue;                            // 入队即标记
            if (t + 1 >= b[nx][ny]) continue;   // 严格早于摧毁时刻
            ti[nx][ny] = t + 1;
            q.push({nx, ny});
        }
    }

    ll ans = INF;                                   // ★6 求 min 的初值
    for (ll i = 0; i < 310; ++i)
        for (ll j = 0; j < 310; ++j)
            if (b[i][j] > 1000 && ti[i][j] != -1)   // ★7 区间判据
                ans = min(ans, ti[i][j]);

    if (ans == INF) cout << -1;                     // ★8 与初值成对
    else cout << ans;
    return 0;
}
```

### 10.2 第 63 行 `if(ans > 1000)`：**对，而且能证明对**

你写的是 `if(ans > 1000) cout << -1;`（不是 `ans == INF`）。这看着像"随手挑了个阈值"，其实**在本题约束下恰好是严格的**：

> **证明**：设存在可达的安全格，取最短合法路径 $p_0=(0,0),p_1,\dots,p_A$（$A$ = 答案，$p_A$ 永不摧毁；沿这条路径到达 $p_i$ 的时刻就是 $i$）。
> 若某个 $p_i$ 是"会被摧毁"的格，合法性要求 $i < dead[p_i] \le 1000$，故 $i \le 999$。
> 于是下标 $i=1000$ 的格**不可能**是"会被摧毁"的格 ⇒ $p_{1000}$ 必然永不摧毁，且它 ≤1000 步可达。
> 所以**只要答案存在，答案 $\le 1000$**；若 $A > 1000$ 就与"答案 $\le 1000$"矛盾。
> 而 `INF = 1e18 > 1000`，因此 `ans > 1000` ⟺ `ans` 从未被更新过 ⟺ 无解。∎

实测吻合：1500 轮随机对拍里，你的版本与 `ans == INF` 版本**一次都没有分歧**。

> ⚠️ 但这条"对"是**借来的**：它默默依赖"摧毁时刻 $\le 1000$"这条题面约束。题面上限若改成 $10^9$，同一份代码立刻开始把真实答案（可能 >1000）误判成 `-1`。**通用写法永远是 `if (ans == INF)`**——行为一模一样、不藏假设、一眼看懂。建议改回去：不是因为它错，而是因为"正确性不该取决于题面常数"。

### 10.3 还剩一个隐患：缺上界判（实测 620 次越界读）

第 46 行只判了 `nx < 0 || ny < 0`。现在 `b` 的初值修好了，BFS 真的能铺满整个网格，于是**必然**会走到坐标 309 再试图迈到 310。探针实测（`test_\01_p2895_user_v2_probe.cpp`，跑 `big_p2895_free.txt`）：

| 探针项 | 实测 |
|---|---|
| BFS 最远走到的坐标 | **309**（下标上限就是 309）|
| 撞到 `nx/ny >= 310` 的次数 | **620** |
| 其中真的读了 `b[310][*]` | **620** |
| 被判据拦下（没写出去） | 620 |
| ★ 真的写了 `ti[310][*]` | **0** |
| 越界写到 `pad[]` 上的元素个数 | **0** |

**结论：今天侥幸无害，但确实是 UB。** 原因是 `b` 后面那块内存里的值恰好让 `(t+1) >= b[310][ny]` 恒真，于是每次都被拦下、从没写出去——这是**内存布局的巧合**。换个编译器 / 优化等级 / 全局变量声明顺序，就可能变成"读到垃圾值 → 判据放行 → 真的写越界 → 静默改掉别的全局变量"。

修法一行（建议直接补上，教材原码也有同样问题）：

```cpp
if (nx < 0 || ny < 0 || nx >= 310 || ny >= 310) continue;
```

### 10.4 一个过期注释

第 19 行注释还写着"每个格子爆炸的时间初始为 1002"，代码已经改成 `1e18` 了。**注释与代码不同步**是排查时的经典陷阱（下次读代码会先被注释误导），顺手改成 `// 初始为 INF，视为永远不会爆炸`。

### 10.5 一句话总结

**逻辑上你这一版是对的**（对拍 1500 轮 0 错）。但——见 §十一：**它在测评机上会 RE**，原因正是 10.3 那处越界。所以最终结论以 §十一 为准。

## 十一、后续：测评机 RE —— 就是 §10.3 那处越界（同日下午补记）

### 11.1 先抓住最关键的线索：WA → RE 的"转变"本身

| 阶段 | 代码状态 | BFS 会不会走出去 | 越界会不会发生 | 判题结果 |
|---|---|---|---|---|
| 第一次提交 | `memset(b,1002,...)`，`b` 全是负数 | **不会**（判据 `1 >= -1.5e18` 恒真，一步没走）| **从不发生** | WA |
| 改对之后 | `b` 初值 `INF`，逻辑完全正确 | **会**（真的铺开到坐标 309）| **发生了**（读到 `b[310][*]`）| **RE** |

> **"把逻辑修对之后，判题反而从 WA 变成 RE"——这是越界的经典信号。**
> 原来不是没有 bug，是**那条路的代码根本没被执行到**。修好前半个 bug，后半段的 UB 才第一次暴露出来。

### 11.2 实测：上界护栏到底拦住了什么

探针 `test_\01_p2895_fixed2_probe.cpp`（与加固版逻辑相同，只多两个计数器），跑"起点附近全空、BFS 铺满整个网格"的用例 `big_p2895_free.txt`：

| 程序（网格 N=310）| 上界护栏触发次数 | 实际入队格子数 |
|---|---|---|
| 你的版本（没有上界判）| —（这 620 次就是**真的读了 `b[310][*]`**）| — |
| 加固版（补上 `nx>=N \|\| ny>=N`）| **620 次**，全部就地 `continue` | 96,099 / 96,100 |

620 这个数字和 §10.3 探针测到的"真的读了 `b[310][*]` 620 次"**完全对上**：护栏拦住的，正是原来访问界外的那 620 次。

### 11.3 为什么本地 620 次越界毫发无伤，测评机却 RE

本地那次越界读到的是 `b` 后面那块内存（恰好是相邻全局 / `.bss` 的零），值正好是 `-1` 或 `0`：

```cpp
if ((t + 1) >= b[310][ny] || ti[310][ny] != -1) continue;   // 1 >= -1 恒真 → 每次都被拦下
```

连**写**都没发生（§10.3 探针：`写 ti[310][*] = 0 次`）。但这纯粹是**内存布局的巧合**：换编译器、换优化等级、换全局变量声明顺序、32 位还是 64 位、`.bss` 结束处离页边界多远……只要同样的读取返回一个"比 `t+1` 大"的值，判据就会放行 → 真的走到 `ti[nx][ny] = t + 1` 写出界 → BFS 顺着 `x=310,311,…` 一路往外走 → 直到踩到未映射内存 → **SIGSEGV / 0xC0000005 → RE**。

本地实测的两面性（同一份你的代码）：

| 数据 | 本地结果 |
|---|---|
| 坐标全合法（≤300）、BFS 铺满全网格 | 输出 0，退出码 0 —— **看起来一切正常**（620 次越界被侥幸拦下）|
| 坐标上限 315 / 320 / 400 / 700 / 1000 | **退出码 -1073741819 = 0xC0000005 崩溃** |

> ⚠️ **"本地跑通"不能作为"没有越界"的证据。** 越界是 UB：行为由内存布局决定，同一份代码在 A 机器上"正常"、在 B 机器上 RE，是完全正常的事。

### 11.4 加固版：`test_\01_p2895_fixed2.cpp`（建议直接交这一版）

相对你现在 `01.cpp` 的差别只有三点（★）：

### 11.5 交了加固版之后的三种结果，分别怎么办

| 现象 | 说明 | 下一步 |
|---|---|---|
| **AC** | 根因确认 = 越界 | 完成。把 §11.6 那条教训记住 |
| **变成 WA**（不再 RE）| 说明数据里存在 **> 309 的坐标**（题面写 0 ≤ Xi,Yi ≤ 300，但测评数据未必守规矩）；输入侧护栏把它们"忽略"了，答案自然偏大 | 把 `#define GRID_N 310` 改成 **1010** 再交（`01_p2895_fixed2.cpp` 里就这一行），大网格会真正把它们算进去 |

> 附带一条：如果测评机给的是"**RE**"而你的程序**一行输出都没有**，那基本可以断定是崩溃（而不是答案不对）；若它有输出但还是 RE，就要考虑是不是**多组数据没读完**或**退出码非 0**。

### 11.6 这次要记住的三条（跨题通用）

1. **网格搜索的四个方向要一次判完**：`nx < 0 || nx >= N || ny < 0 || ny >= N`。只判 `< 0` 是最高频的漏判。
2. **判题从 WA 变 RE，先怀疑"新走到的那条代码路径上有没有越界"**——而不是怀疑算法。
3. **本地不崩 ≠ 没有越界**。越界是 UB，行为由内存布局决定。判断标准只有两个：代码里**每个下标**是否都有证明；以及**探针/护栏计数**是否为零。
