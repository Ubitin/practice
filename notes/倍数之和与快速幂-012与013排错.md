# 两题排错 · 012（倍数之和）与 013（a^b mod m）

> **触发点**：你让我看 `test_\012.cpp`、`test_\013.cpp` 两题。
> **一句话结论**：
> - **012：你的 bug 已经修对了**（`ans = 0` 移到循环里 ✅）——但**会 TLE**：`for(i=3;i<n;++i)` 在 `T ≤ 1e5, n ≤ 1e9` 下要跑约 **1e14 次**（本机实测单组 `n = 1e8` 就要 **83 ms**，外推 ≈ **23 小时**）。必须用**等差数列 + 容斥**做 O(1)。
> - **013：不是笔误，是做法错**。`pow(a,b)` 返回 **double**（浮点幂），`a,b ≤ 2^63` 时结果早就超出 double 的表达范围 ⇒ 转 `long long` 是 UB。**实测 180/180 全错**；`2 63 1000000007` 正确是 `291172004`，你的程序输出 **`-291172004`**（符号错了，绝对值恰好对）。必须用**快速幂**。

## 一、012：小于 n 的自然数中 3 或 5 的倍数之和

### 1.1 你改对的地方（这处上次已经确认过）

```cpp
cin>>t;
while(t--){
    ans = 0;          // ★ 这次初始化对了（上一版这个 bug 让 10/100 输出 23/2341）
    cin>>n;
    ...
}
```
⇒ 实测 `10 / 100 / 10` 三组输出 `23 / 2318 / 23`，**与正确答案一致 ✅**。

### 1.2 剩下的问题：逐个枚举必然 TLE

```cpp
for(ll i = 3;i < n;++i){ ... }      // 每组 n-3 次
```

| 量 | 数值 |
|---|---|
| 单组 `n = 1e9` | 约 `1e9` 次循环 |
| `T = 1e5` 组 | 约 **1e14** 次循环 |
| 本机实测 | 单组 `n = 1e8` 用 **83 ms** ⇒ 外推 `T×1e9` ≈ **23 小时** |

### 1.3 正解：等差数列 + 容斥，O(1) 每组

```text
m(k) = (n-1)/k              // < n 的 k 的正倍数个数（"小于 n"⇒ 必须减 1）
S(k) = k * m(m+1)/2         // 这些倍数之和（k+2k+...+mk）
ans  = S(3) + S(5) - S(15)  // 15 的倍数被数了两遍，减一次
```

```cpp
ll sumMul(ll n, ll k) { ll m = (n - 1) / k; return k * m * (m + 1) / 2; }
// 每组：
cout << sumMul(n,3) + sumMul(n,5) - sumMul(n,15) << "\n";
```

**实测**：
| 验证 | 结果 |
|---|---|
| 官方样例 `2 / 10 / 100` | `23 / 2318` ✅ |
| **vs 暴力枚举 400 组随机 `n ≤ 3000`** | **不一致 0 ✅** |
| 极限 `T = 1e5, n = 1e9` | **64 ms**，输出 10 万行（首行 `233333333166666668`）✅ |
| 答案量级 | `n = 1e9` 时 ≈ `2.33e17` ⇒ **必须 `long long`**（`int` 上限才 2.1e9） |

## 二、013：`a^b mod m`（`1 ≤ a,b,m ≤ 2^63`）

### 2.1 你的代码

```cpp
ll a, b, p;
cin >> a >> b >> p;
ll temp = pow(a, b);        // ← ★ 问题就在这一行
ll ans = temp % p;
cout << ans;
```

| 出错层次 | 说明 |
|---|---|
| **① 做法错（主因）** | `std::pow(double, double)` 返回的是**浮点幂**。`a^b` 一旦超过 `2^53 ≈ 9e15` 就丢精度，超过 `1.8e308` 直接变 `inf`；把 `inf` 或超范围浮点转成 `long long` 是 **UB**（未定义行为） |
| **② 即使换成整数快速幂，还有隐藏坑** | 朴素写成 `res = res * a % m`，当 `res` 和 `a` 都接近 `2^63` 时，`res * a ≈ 1.7e38` **远超 `LLONG_MAX ≈ 9.2e18`** ⇒ 溢出。必须用 `__int128`（或 `unsigned long long`）中转 |

### 2.2 实测：为什么"样例能过、评测全错"

| 输入 | 正确（Python `pow(a,b,m)` 独立核对） | 你的代码 | 判定 |
|---|---|---|---|
| `2 10 9`（官方样例） | 7 | **7** | ✅ 骗过你 |
| `3 20 1000` | 401 | **401** | ✅ 仍然对（`3^20 = 3.49e9`，double 还没崩） |
| `2 63 1000000007` | **291172004** | **-291172004** | ✘ **符号错了、绝对值恰好对** |
| `9223372036854775808 ×3`（题面上限 `2^63`） | 0 | **-102795784084288** | ✘ 完全不沾边 |
| **随机 180 组**（小/中/贴近 `2^63` 各 60 组） | —— | **错 180 / 180** | ✘✘ |

⭐ **"样例 2 10 9 能过"是最好的陷阱**：`2^10 = 1024` 这么小，double 当然算得准。**幂运算题的样例几乎永远不会超过 `2^53`**，所以样例全过毫无意义。

### 2.3 正解：快速幂（二进制拆指数，边乘边取模）

**思路**：把指数 `b` 写成二进制。例如 `a^13 = a^8 · a^4 · a^1`（`13 = 1101₂`）。
从左往右扫二进制位，维护 `a^(2^k)`（不断平方），遇到 1 就乘进答案，**每次乘法后立刻取模**。

```cpp
using ull = unsigned long long;
ull mulmod(ull a, ull b, ull m) { return (ull)((__int128)a * b % m); }  // ★ 防乘法溢出
ull power(ull a, ull b, ull m) {
    ull res = 1 % m;          // ⚠️ m 可能为 1，此时答案必须 0
    a %= m;
    while (b) {
        if (b & 1ULL) res = mulmod(res, a, m);
        a = mulmod(a, a, m);
        b >>= 1;
    }
    return res;
}
```

**复杂度** `O(log b)` ⇒ `b ≤ 2^63` 时最多 **63 次迭代**，比任何枚举都快。

**为什么 `mulmod` 用 `__int128`**：`(2^63) × (2^63) = 2^126 ≈ 1.7e38`，`long long` 装不下（上限 9.2e18），而 `__int128` 能装到 `1.7e38` 级别 ⇒ GCC 里 `__int128` 是这道题最省事的写法。
（不想用 `__int128` 的话，`unsigned long long` 配合"把其中一个数拆成两个 32 位半"的乘法也能做，但代码长得多。）

### 2.4 实测

| 验证 | 结果 |
|---|---|
| 官方样例 `2 10 9` | **7** ✅ |
| `3 20 1000` | **401** ✅ |
| `2 63 1000000007` | **291172004** ✅（与 Python 独立算的一致） |
| **vs Python `pow(a,b,m)`：180 组（小/中/`2^63` 三档各 60 组）** | 修正版 **错 0 / 180 ✅**（你的原码错 **180 / 180**） |
| `a = b = m = 2^63` | **0** ✅（`m = 1` 的 `1 % m` 保护也验了） |

## 三、这两题连起来看，给你三条可迁移的经验

| # | 经验 | 判据 |
|---|---|---|
| 1 | **看到 `n ≤ 1e9` 就别写 `for`** | 单组就能跑几秒；`T` 组直接爆炸。想"能不能用公式/前缀和/二分" |
| 2 | **看到 `a^b`、`2^k`、`n!` 这类量级，先估数值上限** | `2^63 ≈ 9.2e18` 已经贴 `long long` 上限；`a^b` 那更是天文数字 ⇒ **必须边算边取模**（快速幂） |
| 3 | **`pow` 是浮点函数，不是整数幂** | `(ll)pow(a,b)` 只在 `a^b < 2^53` 时才碰巧对。**竞赛里一切"整数幂"都用快速幂**；同理 `sqrt` 后要 `+0.5` 或改用整数判断 |
| 4 | **乘法溢出比加法溢出更容易漏** | `a`、`b` 各自都在 `long long` 范围内，**乘积却可能爆**。看到 `a*b` 且 `a,b` 都可能是 `1e9+`，就要问一句"要不要 `__int128`" |

⚠️ 顺带一句：012 的教训和上周那条一模一样——**"样例全对"证明不了任何事情**。
012 的样例（`10`、`100`）你的代码**完全算得对**，错的是**数据规模**；013 的样例（`2^10`）你的代码也**完全算得对**，错的是**数值范围**。⇒ **自检三问**（数组开够了吗 / 初值对吗 / 边界测了吗）后面应该再加一问：**"最大数据我试过吗？"**

## 四、自查

<details><summary>Q1：012 的样例为什么会"全对"？</summary>

因为样例 `n = 10`、`n = 100` 都很小，逐个枚举当然算得出正确答案。
它的错**不在逻辑**，而在**复杂度**——`T ≤ 1e5` 与 `n ≤ 1e9` 这两个上界相乘才是杀手。
⇒ 检查复杂度时要**把最坏情况乘出来看**：`1e5 × 1e9 = 1e14`，看见这个数就知道必须优化。

</details>

<details><summary>Q2：013 为什么小数据能过、大数据全错？</summary>

`double` 有 **53 位有效位**，能精确表示的整数上限是 `2^53 ≈ 9.007e15`。
- `2^10 = 1024`、`3^20 ≈ 3.5e9`：都远小于 `2^53` ⇒ 精确 ⇒ 答案对；
- `2^63 ≈ 9.22e18`：超出 `2^53` ⇒ **精度丢失**，而且 `2^63` 恰好是 `LLONG_MIN` 的绝对值 ⇒ 转 `long long` 后显示成负数（`-291172004` 就是这么来的）。

</details>

<details><summary>Q3：为什么 `-291172004` 和正确答案 `291172004` 只差一个负号？</summary>

`2^63` 对 `long long` 来说是"溢出到最小值"的位置：`(long long)9.223372036854776e18` 在 x86 上通常得到 `LLONG_MIN = -9223372036854775808`（二进制 `1000...0`）。
对一个负数做 `%`，C++ 的结果**符号跟被除数**（负数）⇒ 于是得到 `-291172004`。
**这不是巧合，而是"高位溢出后又被符号位解释"的典型指纹** —— 遇到"答案只是符号错了"，第一反应就该是"有符号整数溢出了"。

</details>

<details><summary>Q4：快速幂为什么能保证不溢出？</summary>

因为**每次乘法之后立刻取模**，参与下一次乘法的数永远在 `[0, m)` 内。
所以唯一可能溢出的地方是"两个 `< m ≤ 2^63` 的数相乘"，那一步用 `__int128` 兜住即可（`2^126 < 2^127`）。
⚠️ 注意 `a %= m` 要放在循环前，否则第一步 `res * a` 就可能已经溢出。

</details>

<details><summary>Q5：`res = 1 % m` 里的 `% m` 能不能省？</summary>

不能。若 `m = 1`，任何数模 1 都是 0，而 `res = 1` 会让函数返回 1 ⇒ WA。
`1 % m` 这一写法就是专门处理 `m = 1` 的（题面允许 `m = 1`）。实测 `a = b = m = 2^63` 那组我另外验了 `m = 1` 的返回 0。

</details>

<details><summary>Q6：如果题目把范围改成 `a,b,m ≤ 2^64`（超过 `long long`）怎么办？</summary>

那就不能用 `long long` 了，要用 `unsigned long long`（可表示到 `2^64 - 1`），乘法仍需 `__int128`（它能表示到约 `2^127`，装得下两个 `2^64` 的乘积）。
若连 `__int128` 都不够（比如模数是 `10^18` 量级且要做更复杂的运算），就要写"龟速乘"（把乘法拆成加法，`O(log)` 次）——但那是 `__int128` 不存在时的备选方案。
</details>
